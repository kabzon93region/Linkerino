# Linkerino — план исправлений, улучшений и оптимизации

> **Для исполнителя:** выполнять задачи по порядку зависимостей, с независимым аудитом каждого среза. Чекбоксы — будущая работа, не результаты текущей проверки.

**Цель:** сначала исключить удаление неподтверждённых данных и сократить риск раскрытия доступа; затем улучшить восстановление, совместимость и скорость без снижения качества сверки.

**Архитектура:** один переносимый `Linkerino.exe` для GUI и CLI; все решения о записи и удалении принимает движок. Сохранить порядок «временная копия → сверка → публикация → резерв → ссылка → проверка → удаление», но сделать разрешение на удаление явным и привязанным к проверенным объектам, а не только к строкам путей.

**Стек и база:** Rust 2.2.0, Win32, egui/glow, коммит `372bd26`. Классическая сборка C++ 1.1 просмотрена по общим рискам, не построчно. Исходники и выпуски этой задачей не меняются.

**Спецификация:** [инварианты переноса](../specs/2026-11-24-linkerino-design.md#L14-L29) с поправками [1.1](../specs/2026-11-24-linkerino-design.md#L41-L54) и [2.x](../specs/2026-11-24-linkerino-design.md#L56-L73); [публичные обещания](../../../README.md#L59-L95), [карта кода](../../architecture/CODE_MAP.md).

## Общие ограничения

- Не перезаписывать существующее назначение. При сомнении сохранять оригинал или резерв и сообщать его полный путь. Журнал никогда не служит разрешением на автоматическое удаление.
- Переносимость и один EXE для Rust GUI/CLI; без новых зависимостей для запуска без отдельного согласования. Старые Windows и файловые системы заявлять отдельно по каждой сборке, только после реального прогона.
- Все проверки — на специально созданных временных деревьях, виртуальных дисках или тестовых шарах. Не использовать реальные папки владельца. Для фиксации тестовых условий использовать внутренние заглушки файловой системы и синтетические данные.
- SHA-256 и независимая сверка читаемой копии обязательны; буферизация, кеширование и параллелизм не должны убирать проверки на границах операции.

## Границы доверия и точки проверки

| Откуда приходят данные | Куда попадают и чем ограничивать |
|---|---|
| Поля GUI, диалог выбора, аргументы CLI → предварительный план | Имена ведут к созданию файлов, переименованию, ссылке и удалению. Предпросмотр не даёт полномочий на запись; перед изменениями нужна проверка реальных объектов, включая родителей и том. |
| Дерево источника, атрибуты, DACL, потоки и цели ссылок | Снимок, файлы копии, сверка и очистка. Считать вход недоверенным; не путать метаданные и содержимое, не следовать по неожиданным перенаправлениям и не терять кодировку имён. |
| Каталог назначения и ответ файловой системы или SMB | Фиксация копии и решение об удалении. Возможность записать файл не доказывает устойчивость итогового имени, сохранность дополнительных данных или надёжность идентификатора. |
| Папка журналов, окружение, повреждённые записи | Только диагностика для GUI/CLI. Нужны раздельные поля, ограничение размера и проверка принадлежности служебных файлов; приватные пути не публиковать в CI или отчётах без очистки. |

## План внедрения

**Порядок:** T1 → T2; T3, T4 и T5 проектировать отдельными срезами с общими правилами T2; включить автоматическую очистку только после всех пяти. T6–T10 — после ворот P0; T11 — параллельное решение по классическому выпуску; T12 — после фиксации безопасного поведения. Если надёжное удержание или сверка объектов на конкретной ФС недоступны, штатный результат — ссылка с сохранённым резервом либо отказ до переключения, а не более слабая проверка.

### T1 · Проверка путей и владение временной областью (P0) — сделано 2026-11-27
- [x] Сохранить `build_plan` для предпросмотра без записи. Привязать план, который подтверждает пользователь, к идентификаторам исходного каталога и родителя назначения. На входе `execute` сверить, что это те же объекты, и заново проверить запрет корней и системных каталогов, цепочку родителей и вложенность. При смене объекта прекратить операцию до изменений; в GUI запросить новое подтверждение для нового плана. Использовать сравнение компонентов, безопасное для Unicode и учитывающее правила регистра ФС; спорные алиасы не принимать. Не разрешать произвольно заданные извне служебные пути.
- [x] Создавать временную область эксклюзивно с безопасными правами; её идентичность и учёт созданных объектов держит движок. Очистка не следует по неожиданным перенаправлениям; при неуверенности ничего не удалять и показывать путь. Реализация: `create_dir_new`, сверка идентификатора корня при очистке, каждый объект открывается своим дескриптором и удаляется через него, каталоги удерживаются дескриптором без `FILE_SHARE_DELETE` на всё время обхода.
- [x] Приёмка: некорректный план, в том числе с изменившимся идентификатором при том же пути, не меняет ни исходный объект, ни чужой каталог; коллизия не считается успехом; обычное копирование и отказ до публикации проходят в [интеграционных тестах Rust](../../../rust/tests/engine_tests.rs). Файлы: [engine.rs](../../../rust/src/engine.rs), [win.rs](../../../rust/src/win.rs), [main.rs](../../../rust/src/main.rs).

### T2 · Безопасное переключение, откат и очистка (P0, после T1) — сделано 2026-11-27
- [x] Использовать повторно проверенные дескрипторы объектов и цепочек каталогов, неразрушающие проверки без перехода по неожиданным ссылкам и операции над тем же проверенным объектом. Для каждого элемента подтверждать идентичность и неизменность обеих сторон: содержимое, полный набор потоков, существенные метаданные/ограничения доступа и тип объекта. Удерживать эти гарантии от последней сверки до фактического удаления элемента, а не только до вызова на удаление. Не изменять атрибуты внешних имён жёстких ссылок. Если ФС не даёт удержать эти гарантии, не удалять.
- [x] Откат не удаляет объект, если не доказано, что ссылку создала именно эта операция. Отдельно показывать результат восстановления исходного имени, резервный и конечный пути. Не перезаписывать конфликтующий объект и никогда не восстанавливать неполный резерв.
- [ ] Приёмка: изменения обеих сторон, отказ отката и потеря связи останавливают очистку, оставляют данные и дают правдивый итог. Отдельно проверить интервал после последней сверки: если удержание гарантий до удаления невозможно, удаление не начинается для элемента, его данные и потоки остаются в резерве.
